## 一、Treasury 全栈交付与 Agent 提效：人员、职责、亲手实现 vs 公司已有能力

### 1.1 全栈交付：参与人数与职责

| 方向 | 参与人数 | 各自负责 |
|------|----------|----------|
| WebApp 金融产品（前端全栈交付） | **1 人（本人）** | 应用整体设计：服务鉴权、数据存储到产品交互的端到端交付 |
| 数据 / 服务端对接 | **两个服务端团队** | 依托公司金融系统做监控与离线计算，将重要数据落表，供 WebApp 使用 |

本人在 WebApp 侧的五个主要职责：

1. **公司及用户银行账户**的查询与操作  
2. **公司账户资金**的报表与离线统计分析  
3. **交易流水**的记账与对账  
4. **闲余资金**的投资与流动审查  
5. **各国资金池**的查询与调动  

### 1.2 五个微服务的拆分

- **拆分方式**：由原单体服务应用拆为 **五个独立 Server App**，各自连接数据库、独立部署。  
- **原则**：保持原有业务逻辑不变，重点是工程迁移与旧技术债清理。  
- **复杂度判断**：拆分本身偏工程迁移，业务逻辑边界沿用既有职责划分（与上列五项职责对应）。

### 1.3 Agent 提效：参与人数与背景

| 方向 | 参与人数 | 说明 |
|------|----------|------|
| Agent 提效方案设计与落地 | **1 人（本人）** | 独自设计 Skill / Subagent 体系与交付流水线 |
| 平台与周边能力 | 公司已有工具链 | 在线 Agent 开发工具、文档系统、需求系统等 |

**背景**：WebApp 需求堆积、人力不足，测试与联调成本持续上升。目标是把开发流程从「本地 Agent」推进到「云端 Agent」，并与公司已有协作工具打通。

### 1.4 亲手设计与实现 vs 沿用公司已有能力

| 能力 | 归属 | 说明 |
|------|------|------|
| Skill / Subagent 机制与仓库内规范 | **亲手设计与实现** | 按开发流程规范设计 Skill 与 Subagent；机制落在仓库中，在线 Agent 通过读取仓库 `Agent.md` 加载整套规则 |
| Planner / Developer / Tester / Deliver 四个 Subagent | **亲手设计与实现** | 见下表 |
| 开发 / 自动化测试 / 工具 / 设计 四类 Skill | **亲手设计与实现** | 见下表 |
| 在线 Agent 开发平台 | **公司已有** | 云端 Agent 运行与协作入口 |
| 文档、需求系统（如 Ticket） | **公司已有** | Planner 可监控 Ticket；结果回写 Ticket |
| GitLab CI / 部署 Job | **公司已有** | Tester / Developer 对接部署状态与测试环境发布 |
| Atlassian 等协作工具接入方式 | **公司已有能力 + 本人封装为工具 Skill** | 工具使用方法沉淀为 Skill，自动化日常部署与协作 |

### 1.5 Subagent 设计（亲手实现）

| Subagent | 职责 |
|----------|------|
| **Planner** | 承接需求：产品经理可上传文档，或 Agent 监控 Ticket；多轮补充上下文、锁定范围；产出 `plan.md`（含需求范围、代码审查结果、测试 case 列表）交给下游 |
| **Developer** | 以 TDD 为准：按 `plan.md` 先写前端单测，TDD 循环完成前端；用 mock 数据在 sandbox 跑自动化验证；再以同样方式完成后端；全通过后提交代码，经 GitLab Job 部署到测试环境 |
| **Tester** | 检查 GitLab Job 部署状态；通过后进入测试环境做端到端测试；整理结果写入 Ticket；失败则回到上一环节重新开发 |
| **Deliver** | 串联全流程：监控各步状态，经 Slack 通知团队；检查每步产出是否符合预期（是各 Subagent 的编排组合） |

### 1.6 Skill 设计（亲手实现）

| Skill | 内容 |
|-------|------|
| **开发 Skill** | 仓库代码细节、开发习惯、封装组件；代码书写准则与 TDD 准则（含 TDD Guard、TypeScript、GraphQL、权限系统、服务端协议渲染等） |
| **自动化测试 Skill** | 技术规则：Playwright CLI + 测试账号；分步验证与截图；列表项分别截图并注释；可访问性与键盘操作覆盖 |
| **工具 Skill** | 公司工具用法：GitLab、Atlassian 等，打通部署与日常协作自动化 |
| **设计 Skill** | 产品交互、视觉、流程等设计细节梳理，供 Agent 对齐产品标准 |

### 1.7 Slack Bot 接入

- **亲手设计的部分**：Deliver Subagent 中的状态监控与通知语义（何时通知、通知什么、如何与流水线步骤绑定）。  
- **沿用公司已有能力**：Slack 通道与基础 Bot/集成能力；在此之上把通知接到交付编排里。

## 二、跨端核心页面加载时长下降约 80%：关键改动、口径与未继续优化的原因

### 2.1 背景与问题

- **场景**：非发达国家用户页面加载很慢。  
- **量级**：较差国家 **P95 可达约 10s**。  
- **根因（分析结论）**：移动端 **浏览器/容器启动时间长** + **页面脚本加载时间长**，两者 **串行**，用户渗透率长期偏低。

### 2.2 主要带来收益的改动（两条路线）

| 路线 | 做了什么 | 效果 | 本人角色 |
|------|----------|------|----------|
| **路线 A：迁移到 Lynx 跨端渲染** | Web 浏览器方案迁到 Lynx | 约一个月内上线数据最差的 **三个国家**，**P95 达到秒开**（相对原先约 10s 量级，对应「加载时长下降约 80%」量级） | **带小组做技术评审与方案落地** |
| **路线 B：资源预加载** | 脚本离线下载、容器预加载等 | 提升有限；实验数据对 **最终渗透率** 影响不明显 | 团队并行路线 |

**结论口径上的主贡献**：**Lynx 跨端迁移**是加载时长大幅下降的主因；预加载路线收益有限，不是「约 80%」故事的主叙事。

### 2.3 结果所在国家、页面与测量口径

| 维度 | 说明 |
|------|------|
| **国家** | 优先上线 **性能数据最差的三个国家**（非发达国家中加载表现最差的一批） |
| **页面** | **跨端核心页面**（业务主路径核心页，非全站所有页） |
| **测量口径** | **页面加载时长 P95**；优化前较差国家约 **10s**，优化后目标/结果为 **秒开** |
| **对比维度** | 同时关注对 **用户渗透率** 的影响（预加载路线在渗透率上收益不明显） |

> 若笔试需要写死国家名/具体页面名/精确埋点字段，需补充业务侧正式指标名与实验文档；当前素材未给出具体国别列表与页面 URL。

### 2.4 优化后仍慢或收益不明显的页面卡在哪里？为何没继续优化？

| 现象 | 卡点 | 未继续优化的原因 |
|------|------|------------------|
| 与发达国家对比，各项时长仍有差距 | **容器启动时间**、**资源加载时间** | 主要取决于 **用户手机性能** 与 **Lynx 容器性能**，业务团队难以控制 |
| 预加载等手段 | 启动与加载链路仍受设备/容器约束 | 实验显示对渗透率提升不明显，投入产出比不足 |

## 三、激励「百元玩法」拆成配置 / UI / 玩法三层：触发问题、最终方案与放弃的备选

### 3.1 真实需求 / 线上问题（拆分动机）

- **业务目标**：激励多国用户拉新、拉活，发放大额现金奖励。  
- **约束**：所有 **UI 元素**与 **数值金额**需符合各国文化与节日氛围。  
- **痛点（真实问题）**：元旦/圣诞等节日下，日韩、欧美、非洲等差异明显；以往多用 **代码里 if/国家判断** 渲染不同组件，需求日积月累后 **难维护、难复用**。  
- **以本玩法为首例**：主动抽离玩法逻辑与 UI，走向可配置化。

### 3.2 最终怎么拆、怎么解决

| 层 | 职责 |
|----|------|
| **配置层** | UI 元素统一推到 **配置平台**；各国素材、文案、金额等可配置下发 |
| **UI 层** | 前端固定整体界面与交互结构，不按国家堆叠整套页面组件 |
| **玩法层** | 玩法逻辑用 **状态机** 维护；向状态机注入各国所需接口与素材接口 |

**效果**：多国家配置可快速上线，设计元素可沉淀、产品可复用，开发人力更易协调。

### 3.3 当时考虑过的方案，以及为何没选

| 方案 | 是否采用 | 原因 |
|------|----------|------|
| **多页面开发**（各国/各节日单独做页） | **未选** | 不利于设计元素沉淀与产品复用；更难协调开发人力 |
| **配置方案**（配置 + UI 结构 + 状态机玩法） | **采用** | 虽初始开发周期更长，但长期维护与多国复用成本更低，符合业务节奏 |

## 口述要点（可选）

1. **Treasury**：WebApp 全栈 1 人；微服务五拆偏迁移；Agent 方案本人设计，平台/CI/Ticket/Slack 基建靠公司。
