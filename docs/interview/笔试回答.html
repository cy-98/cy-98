一、Treasury 全栈交付与 Agent 提效

1.5 Subagent（亲手设计）

Subagent职责
Planner 承接需求（上传文档或监控 Ticket）；多轮补充上下文、锁定范围；产出 plan.md（需求范围、代码审查结果、测试 case 列表）
Developer 按 TDD：依 plan.md 先写前端单测并完成前端；sandbox + mock 验证 case；再完成后端；全通过后提交，经 GitLab Job 部署测试环境
Tester 检查部署状态；测试环境 E2E；结果写入 Ticket；失败则回到上一环节重做
Deliver 串联全流程：监控各步状态，Slack 通知团队，检查产出是否符合预期（各 Subagent 的编排组合）

二、跨端核心页面加载时长下降约 80%

题目关注：主要改动、国家/页面/测量口径，以及仍慢或无收益页面卡在哪里、为何未继续优化。

2.1 背景与问题

  • 非发达国家用户加载很慢；较差国家 P95 约可达 10s。
  • 根因：移动端浏览器/容器启动与页面脚本加载均偏长，且两者串行，渗透率长期偏低。

2.2 主要带来收益的改动

路线内容效果本人角色
A. Lynx 跨端迁移 Web 浏览器方案迁到 Lynx 跨端渲染 约一个月上线数据最差的三个国家，P95 达到秒开（相对约 10s，对应「下降约 80%」量级） 带小组做技术评审与方案落地
B. 资源预加载 脚本离线下载、容器预加载等 提升有限；对最终渗透率影响不明显 团队并行路线

主贡献结论：加载时长大幅下降主要由 Lynx 跨端迁移带来；预加载不是「约 80%」的主叙事。

2.3 国家、页面与测量口径

维度说明
国家优先上线性能数据最差的三个国家（非发达国家中加载最差一批）
页面跨端核心页面（业务主路径核心页，非全站）
口径页面加载时长 P95；优化前较差国家约 10s，优化后秒开
业务结果同时观察用户渗透率；预加载路线在渗透率上收益不明显

若笔试需要写死国家名、具体页面名或精确埋点字段，需补充业务侧正式指标名与实验文档；当前素材未给出具体国别列表与页面 URL。

2.4 仍慢 / 无收益的卡点与未继续优化原因

现象卡点未继续优化的原因
相对发达国家仍有差距 容器启动时间、资源加载时间 主要取决于用户手机性能与 Lynx 容器性能，业务团队难以控制
预加载等手段收益弱 启动与加载链路仍受设备/容器约束 实验对渗透率提升不明显，投入产出比不足

三、激励百元玩法：配置 / UI / 玩法三层拆分

题目关注：哪一个真实需求或线上问题促使这样拆；最终如何解决；还考虑过什么方案、为何未选。

3.1 触发拆分的真实问题

  • 业务目标：多国用户拉新、拉活，发放大额现金奖励。
  • 约束：UI 元素与数值金额需符合各国文化与节日氛围。
  • 痛点：元旦/圣诞等节日下，日韩、欧美、非洲差异明显；以往用代码里的国家判断渲染不同组件，需求堆积后难维护、难复用。
  • 契机：以本玩法为首例，抽离玩法逻辑与 UI，走向可配置化。

3.2 最终方案

层职责
配置层UI 元素统一推到配置平台；各国素材、文案、金额可配置下发
UI 层前端固定整体界面与交互结构，不按国家堆叠整套页面
玩法层玩法逻辑用状态机维护；向状态机注入各国所需接口与素材接口

效果：多国家配置可快速上线；设计元素可沉淀、产品可复用；开发人力更易协调。

3.3 备选方案与取舍

方案是否采用原因
多页面开发（各国/各节日单独做页） 未选 不利于设计元素沉淀与产品复用；更难协调开发人力
配置方案（配置 + UI 结构 + 状态机玩法） 采用 初始开发周期更长，但长期维护与多国复用成本更低

口述三句：① Treasury WebApp 全栈 1 人，微服务五拆偏迁移；Agent 方案本人设计，平台/CI/Ticket/Slack 基建靠公司。② 性能主收益来自 Lynx（最差三国、核心页、P95 约 10s→秒开）；预加载弱；剩余差距在容器与设备。③ 百元玩法因节日多国 if 渲染不可维护 → 配置平台 + 固定 UI + 状态机；弃多页面。
